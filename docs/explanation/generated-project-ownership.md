# Who owns which file in a generated project

A generated project is assembled from two maintained tools plus one thin overlay.
The split explains what a template update may touch, why `pyproject.toml` is never
rendered, and why one line of `main.py` is yours to write.

## Three owners

| Concern | Owner | Files |
|---|---|---|
| The application | native `uv init`, then the project developer | `main.py` |
| Environment, dependencies, lockfile | uv | `pyproject.toml`, `uv.lock`, `.venv/` |
| Interpreter, tool versions, tasks | mise | `mise.toml`, `mise.lock` |
| Standards, checker policy, documentation seeds | Copier overlay | `AGENTS.md`, `ruff.toml`, `mypy.ini`, `pytest.ini`, `zensical.toml`, `README.md`, `docs/`, `tests/`, `.gitignore`, `.copier-answers.yml` |
| Behavioral specifications, change checklists, agent integrations | OpenSpec | `openspec/`, `.opencode/`, `.agents/` |
| Template lineage | Copier | `.copier-answers.yml` |

OpenSpec is the second tool that owns generated files. It is initialized by its own
CLI inside the project, which is why the overlay renders neither the specifications
nor the integration files: the pinned OpenSpec version, not the template, decides what
those look like, and `openspec update` is the command that refreshes them.

## Policy versus resolution

The overlay renders configuration that states *policy*: how to lint, how to
type-check, where tests live, how the site is built. It never renders configuration
that states *resolution*: which packages, which versions, which interpreter.

The reason is write conflicts, not taste. `pyproject.toml` and `uv.lock` are
rewritten by uv whenever a dependency changes. If a template also rendered them,
every `uv add` would create a template conflict, and every template update would
create a dependency conflict. Keeping resolution in uv-owned files means the two
tools never write the same file.

The same rule excludes `main.py`: application code changes for reasons the template
cannot know, and a template that owned it would overwrite the user's work.

## Why the checkers have standalone files

Ruff, mypy and pytest are configured in `ruff.toml`, `mypy.ini` and `pytest.ini`
rather than in `[tool.*]` sections of `pyproject.toml`. A `[tool.*]` section would
put template content inside a uv-owned file, which is exactly the overlap this
design avoids. None of the three files declares a dependency; versions live in
`pyproject.toml` (uv) and `mise.toml` (mise).

## The one project-owned edit

`mypy --strict` fails on the entry point that the pinned uv generates:

```python
def main():            # no return annotation
```

Adding `-> None` is a change to project-owned code, so the creation recipe makes it
explicitly and the integration test applies it as a documented step. Two
alternatives were rejected:

- **Let Copier patch `main.py`.** The overlay would then own application code and
  would conflict with every later edit to that function.
- **Relax the mypy baseline.** A rule set that accepts unannotated functions gives
  up the check most likely to catch a real defect, in exchange for one saved
  character per function.

When a future uv release annotates its scaffold itself, the step disappears — the
tutorial's `assert` makes that visible instead of silently skipping.

## Verification

`mise run check` in a generated project runs the contract below; each command
belongs to the tool that owns it.

```text
uv lock --check                          uv
uv run --locked ruff check .             uv runs Ruff
uv run --locked ruff format --check .    uv runs Ruff
uv run --locked mypy --strict main.py    uv runs mypy
uv run --locked pytest                   uv runs pytest
uv run --locked zensical build --strict  uv runs Zensical
openspec validate --all --strict --no-interactive   mise installs OpenSpec, which validates its own artifacts
```

mise supplies the interpreter and the tools, uv resolves and runs the Python ones, the
checker configuration comes from the overlay, and OpenSpec validates the
specifications it owns. The type-checking target is `main.py` only; widen it in
`mypy.ini` and in the `typecheck` task when modules are added, so both stay in step.

## Reproducibility and its limits

Two lockfiles, one per boundary:

- `mise.lock` fixes the interpreter and CLI releases with checksums.
- `uv.lock` fixes the Python dependency graph with hashes.

Both are generated by their native tools and committed by the project. A template
update changes project files; it does not re-resolve either lockfile.

Not covered, and not claimed:

- **Platforms.** Only Linux x86-64 is verified; `mise.lock` covers `linux-x64`.
- **Release tags.** ai-devkit has no release tag yet. Tag-based provenance is
  exercised with a temporary tagged repository, not with a published release.
- **Byte-identical regeneration.** Each project resolves and commits its own
  `uv.lock`; two projects created minutes apart can differ where the index moved.
  That is why the baseline is recorded as exact versions rather than promised as a
  byte-identical artifact.
- **Template update conflicts.** Copier's conflict handling is native and reviewed
  by a human. Lifecycle testing of conflicting edits is deferred to a later task.
