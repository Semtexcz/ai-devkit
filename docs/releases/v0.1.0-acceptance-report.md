**Why the tag target is not named here.** A report cannot name the commit that contains
the report. Every correction moves `main`, so chasing that value would produce an endless
sequence of documentation commits that each certify the previous one, and the report would
still be stale the moment it was committed. The two values are therefore separate:

- *Reviewed revisions* are the commits whose evidence this report records: `685f041`
  (clean container, sections B and C), `b3b06f2` and `ac62d27` (hosted CI), and
  `ac62d27` as the revision this version was reviewed against.
- The *release-tag target* is the commit a human tags. It must be a reviewed revision, or
  a later commit whose only difference from one is documentation. If anything executable
  changed since the reviewed revision, the affected level below is re-run rather than
  cited.

**Difference in coverage.** The clean-machine run happened on `685f041`. The revision
reviewed immediately afterwards is `b3b06f2`, whose diff covers `README.md`, seven files
under `docs/` and the site navigation in `zensical.toml`; it changes no `mise.toml`, no
lockfile, no Copier template, no test, no application fixture and no workflow. Hosted CI
has run on `b3b06f2` and is green. The later revision `ac62d27` carries the
acceptance-report split between commits and the corrections recorded in A4 and A5; those
diffs are documentation-only as well, and hosted CI is green on it.

That delta describes the changes; it does not transfer evidence. **The clean-machine
PASS below belongs to `685f041` and to no other commit.** The clean-environment run was
not repeated for `b3b06f2` or `ac62d27`, because no technical reason required it: the
executable surface is identical and hosted CI exercises the same checks on the newer
commits. If the delta ever stops being documentation-only, section B has to be re-run on
the new commit rather than cited from this one.

The three levels of acceptance are reported separately and are not merged into a

### A3. Read-only acceptance check

`git diff --exit-code` is the intended read-only check, but it can only be read on a
clean baseline. The task's own documentation edits make this tree intentionally dirty,
so the check was performed in a form that cannot confuse the two:

1. the tree was confirmed clean at `685f041` before any edit;
2. the intentional documentation edits were made;
3. a full verification pass ran (`mise install --locked`, `uv sync --locked`,
   `mise run versions`, `mise run check`, `mise run test-template`); the tracked-file
   set was unchanged by it;
4. the tracked state was then snapshotted as
   `sha256sum(git status --porcelain + git diff)` → `7fd2448e…5f90aa`;
5. `mise run check` ran once more and the snapshot was recomputed →
   `7fd2448e…5f90aa`.

Nothing the verification commands do reaches a tracked file: `.venv/`, `site/`,
`.cache/`, `.pytest_cache/`, `.ruff_cache/` and `.mypy_cache/` are all ignored. The
same guard runs in CI as `test -z "$(git status --porcelain)"`, where the tree is a
fresh checkout and therefore genuinely clean.

#### 2. Verify the base project, then commit it


A Git repository with a clean tree turns everything an agent does into a reviewable

**Git identity prerequisite.** `git commit` needs an author name and an address. A

```bash

```

#### 3. Clone two independent fixtures

Do not copy the base project's directory, and do not use `rsync` or a custom copying
utility to do it more carefully. `cp -a` copies `.venv/` as well, and uv 0.13.7 writes
console scripts into that environment with an absolute shebang — in a checkout of this
repository, `.venv/bin/pytest` begins with `#!/…/ai-devkit/.venv/bin/python`. A copied
environment therefore either runs the *base project's* interpreter or stops working when
the base project moves, and the fixture's `mise run check` would then report on an
environment that nobody created at that path.

Native Git cloning copies committed content and nothing else, so an ignored `.venv/`
cannot travel:

```bash
mkdir -p "$HOME/acceptance"
git clone --local --no-hardlinks \
  "$HOME/acceptance/base project" \
  "$HOME/acceptance/opencode"

git clone --local --no-hardlinks \
  "$HOME/acceptance/base project" \
  "$HOME/acceptance/codex"
```

`--local` keeps the operation on the local object store and `--no-hardlinks` copies the
objects instead of hardlinking them, so the three repositories share no inode that an
agent, or a later `git gc`, could disturb. Each clone records the base project as its
`origin`; nothing in this procedure pushes anywhere.

Each fixture then owns its `.venv/`, `uv.lock`, `mise.lock`, `openspec/`, `.opencode/`
and `.agents/`, so neither session can influence the other's result. Six checks per
fixture, in this order — the last one is the point of cloning at all: regenerating an
environment and re-running the contract must not change a tracked file.

```bash
(
  set -e
  for p in "$HOME/acceptance/opencode" "$HOME/acceptance/codex"; do
    cd "$p"
    test ! -e .venv
    mise trust
    mise install --locked
    mise exec -- uv sync --locked
    mise run check
    test -z "$(git status --porcelain)"
  done
)
```

1. `test ! -e .venv` fails when an environment was copied, which is what `cp -a` used to
   do. A failure here means the fixture came from a directory copy, not from the clone.
2. `mise trust` is required because the fixture path is new to mise, and mise refuses to
   read an untrusted `mise.toml`. Review the file first: it is the project's own
   toolchain, not the devkit's.
3. `mise install --locked` installs the project's pinned Python, uv, Node.js and
   OpenSpec. It installs nothing new when those versions are already in the data
   directory.
4. `mise exec -- uv sync --locked` creates the fixture's own `.venv` from its own
   `uv.lock`, with `UV_NO_MANAGED_PYTHON=1` from the project's `mise.toml` in effect.
   This is the step that replaces a copied environment; every fixture therefore starts
   from none.
5. `mise run check` runs the generated project's contract at its new path.
6. An empty `git status --porcelain` proves the previous steps wrote no tracked file — in
   particular no regenerated lockfile.

The subshell with `set -e` encloses the whole loop, not a single iteration, so the first
command that fails stops the complete fixture preparation procedure: a failure while
preparing or verifying `opencode` ends the run before `codex` is touched, and the
procedure exits nonzero. All six checks must pass for both fixtures before an agent
session starts.
