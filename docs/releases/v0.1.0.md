# ai-devkit v0.1.0 — release candidate

This page describes what v0.1.0 delivers, what has been verified, what has not, and
how a tagged release would be produced. It is a **release candidate**: the automated
and clean-machine acceptance evidence exists, but two live agent acceptance tests
still require a user-authorised authenticated session and are reported as pending in
the [acceptance report](v0.1.0-acceptance-report.md).

Reviewed commit for this document: `685f041be7ba39776bd75039743ddaa6516d19db`.

## What v0.1 delivers

v0.1 is a versioned collection of configurations, engineering rules, documentation
and one small project overlay. It composes maintained tools instead of implementing a
development framework.

| Deliverable | What it is |
|---|---|
| Pinned toolchain | `mise.toml` + `mise.lock` (+ `.mise/locks/`) fix Python, Node.js, uv, OpenSpec, OpenCode and the Codex CLI to exact releases with checksums |
| Python environment | `pyproject.toml` + `uv.lock` fix Copier, pytest, Ruff, mypy and Zensical for the maintainer environment |
| Engineering contract | `AGENTS.md` — reuse-first rules, quality gates, security rules and a Definition of Done |
| Project overlay | `copier.yml` + `templates/python-script-overlay/template/`: rules, checker policy, mise tasks, Diátaxis documentation seeds and ignore rules |
| Specifications and change tasks | OpenSpec initialized natively; `openspec/specs/` and `openspec/changes/` are the only requirement and task record |
| Documentation | A Diátaxis site under `docs/`, built by Zensical in strict mode |
| Verification | `mise run check` (repository) and `mise run test-template` (generation and update lifecycle) |
| Hosted verification | `.github/workflows/verify.yml`, read-only, no secret, no model call |

There is no custom orchestrator, no task database, no LLM gateway and no devkit
update command. Architecture rationale is in
[ADR 0001](../explanation/decisions/0001-minimal-devkit.md) and
[ADR 0002](../explanation/decisions/0002-script-project-overlay.md).

## Supported environment

- **Linux x86-64 only.** `mise.lock` declares `lockfile_platforms = ["linux-x64"]`.
- Verified on Ubuntu 24.04.5 LTS (a disposable container; see the
  [environments section](v0.1.0-acceptance-report.md#environments)) and on the
  `ubuntu-24.04` GitHub-hosted runner.
- Prerequisites supplied by the operating system: Git, `curl`, `tar`, `sha256sum`
  and CA certificates. No `sudo`, no system Python, no Node.js and no global
  package installation are needed.
- macOS, Windows and WSL2 are **not** verified and are not claimed.

Tool additions, removals and rollbacks are described in
[Install the development toolchain](../how-to/install-toolchain.md).

| OpenCode | mise | `mise.toml`, `mise.lock` | 1.19.5 |
| Codex CLI | mise | `mise.toml`, `mise.lock` | 0.163.0 |
| Python packages | uv | `pyproject.toml`, `uv.lock` | Copier 9.19.1, pytest 9.2.0, Ruff 0.17.3, mypy 2.4.1, Zensical 0.0.74 |

mise is installed by hand from its official release archive and is therefore not
covered by `mise.lock`; the tested version is 2026.11.1. The full table, including
why each distribution was chosen, is in
[Tool ownership and pinned versions](../reference/tool-versions.md).

One concern, one owner. mise installs and selects the interpreter; uv resolves
packages and never downloads an interpreter (`python-downloads = "never"`,
`python-preference = "only-system"`, `UV_NO_MANAGED_PYTHON=1`). Copier owns the
overlay and its lineage; it never renders `main.py`, `pyproject.toml`, `uv.lock` or
`.python-version`. OpenSpec owns `openspec/`, `.opencode/` and `.agents/`.

## Create a Python project

The complete walkthrough is
[Create your first Python project](../tutorials/first-python-project.md). In short,
inside an ai-devkit checkout with the toolchain installed:

```bash
mise install --locked
mise exec -- uv sync --locked

mise exec -- uv init --app --no-package --no-workspace --no-pin-python \
  --no-readme --vcs none "$HOME/projects/my script"
mise exec -- uv run --locked copier copy --vcs-ref <tag> --defaults \
  "$PWD" "$HOME/projects/my script"
```

`<tag>` is `v0.1.0` once the tag below exists. Until then `--vcs-ref HEAD` renders the
current checkout and records its commit in `.copier-answers.yml`, which is correct for
a clean tree but not a stable release reference.

Then, in the project: `uv add --dev` the four baseline tools, make the one
project-owned edit (`def main() -> None:`), `mise run lock-tools`, and
`openspec init --tools opencode,codex --profile core`. `mise run check` verifies the
result with seven native commands.

What each layer renders and runs is in
[Generated project: commands and contents](../reference/generated-project.md).

## The OpenSpec workflow

OpenSpec is the only specification and change-checklist system. A change moves
through native commands, with a human or an agent doing the writing:

1. `openspec new change <name>` creates the change directory.
2. The proposal, the delta specification (`## ADDED Requirements` with at least one
   scenario per requirement) and `tasks.md` are written and reviewed.
3. `openspec validate <name> --strict --no-interactive` accepts or rejects them.
4. The code, a regression test and the documentation page are changed.
5. `mise run check` runs the whole contract, including
   `openspec validate --all --strict --no-interactive`.
6. `openspec archive <name>` moves the change to
   `openspec/changes/archive/<date>-<name>/` and writes the requirement into
   `openspec/specs/<capability>/spec.md`.
7. `mise run check` runs again; the specification is now part of the checked baseline.

The worked example is
[Plan, implement and archive one change](../tutorials/spec-driven-change.md); paths,
owners and per-harness invocation are in the
[OpenSpec reference](../reference/openspec.md). Nothing else records tasks: no
backlog file, no status table, no workflow schema.

## What CI and the lifecycle tests verify

`mise run check` (repository): `uv lock --check`; the agent configuration examples
parse; every OpenSpec change and specification validates; the documentation site
builds with no broken internal link.

`mise run test-template` (integration): a project is created with native `uv init` in
a path containing spaces, the overlay is applied from a temporary tagged template
repository, the baseline dependencies are installed, the project's own `uv.lock` and
`mise.lock` are generated by their native tools and installed into a throwaway mise
installation, the interpreter identity is proven through `sys.base_prefix` and
`readlink -f` rather than a version string, OpenSpec is initialized by the project's
own pinned CLI, the application and its smoke test run, the project's `mise run check`
passes, each of six deliberate defects fails the check through the task that owns
that checker, the complete OpenSpec lifecycle from `examples/openspec-change/` runs,
and native `copier update` between two temporary tagged revisions preserves
application code, `pyproject.toml`, `uv.lock` and documentation while leaving a
same-region conflict visible and reviewable.

`.github/workflows/verify.yml` runs the same commands on `ubuntu-24.04` with
`contents: read` and no secret, then fails if verification changed a tracked file.
Hosted runs and their conclusions are listed in the
[acceptance report](v0.1.0-acceptance-report.md); what the pipeline does not prove is
in the [continuous integration reference](../reference/continuous-integration.md).

## Known limitations

- **Linux x86-64 only.** No macOS, Windows or WSL2 support is claimed.
- **v0.1 pins no agent CLI in a generated project.** A project's `mise.toml` pins
  Python, uv, Node.js and OpenSpec. OpenCode and Codex are installed once per machine
  (through this devkit's toolchain or the vendor's installer), not per project.
- **No release tag exists yet.** Copier provenance therefore records the commit a
  project was rendered from; tag-based provenance is exercised only with a temporary
  tagged repository inside the integration test.
- **OpenSpec validation passes vacuously on an empty scope.** A freshly initialized
  project prints `No items found to validate.`; the first specification is what turns
  the check into evidence.
- **No byte-identical regeneration guarantee.** Each project resolves and commits its
  own `uv.lock`; two projects created minutes apart can differ where the index moved.
- **No conflict automation.** Copier conflicts are left inline for a human to resolve.
- **Agent execution is unverified.** Whether each harness really injects `AGENTS.md`
  into its context at runtime is asserted by nothing in this repository.
- **No licence.** v0.1 selects no licence; decide before public distribution.

## Deferred beyond v0.1

- Additional project profiles (library, service) and any second template.
- Packaging or publishing of generated projects.
- Container images, deployment and release automation for ai-devkit itself.
- Agent orchestration, automatic model routing and role-to-model configuration.
- A dashboard, a task database or a custom backlog.
- Cross-platform certification and virtualization infrastructure.
- Cline automation beyond documentation: it stays interface-driven and optional.
- Cezar, whose OpenCode support and permission behaviour were judged unsuitable for
  an assumed security boundary in v0.1.

## Intended tagged-release procedure

**No tag has been created for this candidate, and none may be created by an automated
change** (see `AGENTS.md`). A human performs the steps below after reviewing the
acceptance report.

1. Confirm the acceptance report shows no unresolved **FAIL**, and decide explicitly
   whether the two **PENDING** live agent tests block the release.
2. Confirm the working tree is clean and that the reviewed commit is the one on `main`.
3. Confirm the hosted `verify` workflow is green for that exact commit.
4. Create an annotated tag on that commit and push the tag:

   ```bash
   git tag -a v0.1.0 -m "ai-devkit v0.1.0"
   git push origin v0.1.0
   ```

5. Verify that Copier can resolve the tag by rendering a throwaway project from it and
   reading its provenance:

   ```bash
   mise exec -- uv run --locked copier copy --vcs-ref v0.1.0 --defaults \
     gh:Semtexcz/ai-devkit "/tmp/tag check"
   sed -n '1,12p' "/tmp/tag check/.copier-answers.yml"
   mise exec -- uv run --locked copier check-update "/tmp/tag check"
   ```

   `_commit` must name the tagged revision and `check-update` must report
   `Project is up-to-date!`.

6. Announce the release. Nothing is published to a package index: ai-devkit is a Git
   template source, not a Python distribution.

**Why the tag matters.** `.copier-answers.yml` records `_src_path` and `_commit`, and
`copier update` diffs a project against exactly that revision. A published tag is a
stable, immutable provenance value that exists in the template repository for every
future `copier update`; a commit recorded from an uncommitted working tree is not, and
Copier later fails with `ValueError: Unknown revision`. Projects meant to receive
overlay updates should therefore be created with `--vcs-ref v0.1.0` once the tag
exists. See [Update a project's overlay](../how-to/update-project-overlay.md).
